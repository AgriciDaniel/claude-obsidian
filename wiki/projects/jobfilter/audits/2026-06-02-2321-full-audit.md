### 4. INTAKE FLOW / ENGINE ← ROOT CAUSE DIAGNOSIS

**THE PROBLEM:**

The intake engine has a routing conflict between two handlers for `/api/intake/score`:

| Layer | File | Status |
|-------|------|--------|
| Next.js App Router | `app/api/intake/score/route.ts` | **WINS** (takes priority) |
| Express via Pages Router | `pages/api/[[...path]].ts` → `server/routes/intakeScore.ts` | **DEAD** (never reached) |

**The Next.js route was a stub:**
- Called `scoreIntake()` ✓
- Returned lead object ✓
- **Never called `persistLeads()`** — lead not saved to Supabase ✗
- **Never called `triggerGoldLeadWhatsApp()`** — GOLD leads get no notification ✗
- Always returned `whatsapp: { triggered: false, provider: 'none' }` ✗

**Additional issues:**
1. `decisionScoring.ts:60` returned tier `'BIN'` — not a valid quality label (`'GOLD'|'SILVER'|'BRONZE'|'CHECK'|'SKIP'`)
2. `server/routes/intakeScore.ts:9` only allowed 4 job types (Electrical, Plumbing, Roofing, Building) vs 9 shown in UI — would error on HVAC/Carpentry/Landscaping/Painting/Heat Pumps if Express had been the handler
3. The lead returned had no `qualityLabel` field — just `tier: 'BIN'`
4. After submission, customer redirected to `/leads/{id}` which reads from localStorage — lead exists in CUSTOMER's browser only, tradesman cannot see it in any dashboard

**What was needed (all fixed this run):**
1. Fix `app/api/intake/score/route.ts` to import and call `persistLeads()` and `triggerGoldLeadWhatsApp()`
2. Map tier 'BIN' → 'BRONZE', add `qualityLabel` to response
3. Expand Express job type whitelist to 9 types
4. Fix `decisionScoring.ts` to return 'BRONZE' not 'BIN'

**What still requires founder action:**

### BP-1: Fix scoring threshold inconsistency

> The app has two scoring systems with different thresholds: `server/services/decisionScoring.ts` uses GOLD≥80/SILVER≥50/BRONZE<50, but `leadEngine/scorer.ts` uses GOLD≥90/SILVER≥75/BRONZE≥60/CHECK≥40/SKIP<40. `LeadDetailPage.tsx` shows different copy based on score thresholds (>= 80 = GOLD copy, >= 50 = SILVER copy) which matches the intake engine thresholds but not the scan engine. Create a single source-of-truth file `src/lib/scoreTiers.ts` that exports `getQualityLabel(score: number): 'GOLD'|'SILVER'|'BRONZE'|'CHECK'|'SKIP'` with unified thresholds (suggest GOLD≥80, SILVER≥60, BRONZE≥45, CHECK≥30, SKIP<30). Update all usages: `scorer.ts`, `decisionScoring.ts`, `LeadDetailPage.tsx`, `LeadListPage.tsx`. Do not change the label strings (GOLD/SILVER/BRONZE/CHECK/SKIP). Run `npm run build` after changes.

### BP-2: Persist leads to Supabase for the tradesman dashboard

> The intake form (`/intake/[username]`) creates leads visible only in the customer's browser localStorage. The tradesman cannot see intake submissions in their dashboard. Fix: in `app/api/intake/score/route.ts`, the `username` param is passed from the form but not used to look up the tradesman. Add a Supabase lookup: `SELECT user_id FROM profiles WHERE username = $username`, then store the intake lead with `owner_id = user_id` in the `leads` table. In the tradesman's dashboard (`src/pages/DashboardPage.tsx`), add an "Intake Requests" section that fetches `GET /api/leads/intake-requests` filtered by the logged-in user's `user_id`. The Express route for this should be in `server/routes/intakeRequests.ts`. Schema: the `leads` table already has an `id`, `title`, `trade`, etc. Add `owner_id uuid` column referencing `auth.users.id` if it doesn't exist.

### BP-3: Fix intake lead visibility — tradesman lead list

> After the intake engine fix (leads now persist to Supabase), the tradesman's `/leads` page (`src/pages/LeadListPage.tsx`) reads from localStorage only. Add a hybrid approach: on page load, fetch from `GET /api/leads/my-intake` (new Express route in `server/routes/myIntake.ts`) which queries Supabase for leads where `source = 'Intake'` and `owner_id` matches the auth token. Merge these with localStorage leads, deduplicating by `id`. Display intake leads in a separate "From Your Link" section above the scan results.

### BP-4: Real free-tier scan limit enforcement (server-side)

> The 3 scans/week free limit is enforced via `localStorage` in `FindJobsPage.tsx` which is trivially bypassed (clear localStorage). Add server-side enforcement in `server/routes/leadsSearch.ts`. The `resolveAccessContext()` function already checks Supabase subscriptions — add a scan counter: `upsert` into a `scan_counts` table `(user_id, week_key, count)` and reject with 429 if count > 3 for non-paid users. For unauthenticated requests, use IP-based rate limiting via the existing `rateLimit` middleware.

### BP-5: WhatsApp template messages (approved templates)

> The current WhatsApp implementation (`server/services/sms.ts`) sends free-form text messages. Meta's WhatsApp Business API requires approved message templates for outbound messages (not in response to a user message within 24h). Free-form text will fail with error 132001 "Template name does not exist". Fix: register a message template in Meta Business Manager for GOLD lead notifications. Then update `sms.ts` to use `type: 'template'` with `template: { name: 'gold_lead_alert', language: { code: 'en_GB' }, components: [...] }`. The template must be approved by Meta before it works.

### BP-6: Add subscription gating to lead contact details

> Contact details (phone, buyer name) in `LeadDetailPage.tsx` are shown in full for all users. According to the pricing page, "buyer context" and "WhatsApp delivery" are paid features. Add a paywall: check `useSubscription()` hook (already exists in `src/lib/useSubscription.ts`). If the user is on free tier, blur the phone number and show a "UNLOCK CONTACT — £39/MO" CTA linking to `/pricing`. Keep the score, tier badge, and urgency visible.

### BP-7: Win stats — cross-device persistence

The `ROITracker` component currently reads from `winStore.ts` — update it to accept a prop `{ wins: WinJob[] }` instead of reading localStorage directly.
